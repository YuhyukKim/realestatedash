# 실거래 수집 운영 안내 (1단계)

## 변경 구조와 배포 전 주의

GitHub Actions 수집기 → MOLIT 전체 페이지 확인 → 인증된 업로드 → D1 완전한 스냅샷 → 공개 화면.

- Workers는 MOLIT에 요청하지 않습니다. GitHub runner의 MOLIT 연결은 첫 수집으로 별도 확인해야 합니다. 활용 승인·할당량·접속 허용 문제까지 코드로 해결되지는 않습니다.
- 공개 `/api/trades`, `/api/complex`, `/api/area-summaries`는 읽기 전용입니다.
- 기존 면적별 저장 가격은 유지하고, 새 수집이 완료된 구·월 매매 범위만 교체합니다.
- 구방식 팝업은 외부 API를 직접 조회했으므로 DB에 전체 내역이 들어있다는 보장이 없습니다. **초기 적재 전 새 코드를 배포하면 일부 팝업이 미수집으로 표시됩니다.**
- 검증 환경에서 먼저 배포·수집·확인하고 운영 반영을 승인하세요. 기존 공개 주소/도메인은 바꾸지 않습니다.

## 1. 서버와 GitHub 설정

Worker에 D1 `DB` 바인딩과 서버 Secret `DATA_REFRESH_TOKEN`이 필요합니다. 32자 이상의 충분히 긴 무작위 값으로 만들고 비밀번호를 재사용하지 마세요. 기존 관리자 단지 적재와 같은 토큰 변수입니다.

GitHub 저장소 → **Settings → Secrets and variables → Actions**:

| 위치 | 이름 | 의미 |
|---|---|---|
| Secrets | `MOLIT_API_KEY` | 공공데이터포털 일반 인증키. 매매·전월세 API 각각 활용 신청 승인 필요 |
| Secrets | `DATA_REFRESH_TOKEN` | Worker의 동일한 서버 Secret 값 |
| Variables | `PUBLIC_SITE_URL` | 수집 대상 HTTPS origin. 검증 단계는 검증용 Worker, 운영 전환 후 운영 주소 |
| Variables | `MOLIT_DISTRICTS` | 정기 수집 구를 쉼표로 구분. 예: `마포구,영등포구` |
| Variables | `MOLIT_SCHEDULE_ENABLED` | 첫 검증 전에는 비워두고 자동 수집을 켤 때만 `true` |

`PUBLIC_SITE_URL`은 `https://example.workers.dev` 형태입니다. 경로·쿼리·로그인 정보는 넣지 않습니다. 키/토큰은 Variables가 아니라 Secrets에만 넣습니다. 대화·이슈·스크린샷에 공개하지 마세요.

공개 Worker에서는 MOLIT_API_KEY를 쓰지 않습니다. 기존 Secret을 당장 삭제할 필요는 없습니다. GitHub Secret은 따로 등록해야 하며 Worker Secret이 자동 복사되지 않습니다. 지도·학교 설정은 바뀌지 않습니다.

## 2. 마이그레이션과 전환

새 Drizzle SQL과 메타데이터를 사용합니다. 기존 0000–0002 마이그레이션과 데이터를 삭제/재작성하지 않습니다. 배포가 새 마이그레이션을 먼저 적용하는지 확인합니다.

기존 GitHub 연결 Workers Builds 경로를 사용합니다. 플랫폼 변경이나 기존 중복 배포 경로 정리는 이 PR 범위가 아닙니다.

1. 검증 환경에 새 코드/스키마를 배포하고 검증용 DB·토큰·origin으로 첫 수집을 합니다.
2. 기존 공개 서비스는 유지하고 아래 검증 항목을 확인합니다.
3. 운영 DB 스키마/토큰과 운영 반영 시간을 준비합니다.
4. 운영 배포 후 대표 구의 최근월부터 수집·확인하고 나머지를 순차 적재합니다. 적재 전 기간은 0원이 아닌 미수집입니다.

이 PR은 일시적인 과거 상세 미수집 구간을 없애는 이중 실행까지 포함하지 않습니다. 무중단 데이터 전환이 필요하면 수집 엔드포인트만 먼저 운영에 반영하는 2단계 릴리스를 사용하세요.

## 3. 첫 수집

기본 브랜치에 workflow 반영 후 **Actions → Collect MOLIT snapshots → Run workflow**:

- districts: `마포구`
- from/to: 먼저 같은 월 하나 (예: `202607`)
- kind: `sale`로 매매부터 확인한 뒤 `rent` 또는 `both`

입력한 구·월·유형만 조회합니다. 구가 비어 있으면 전체 서울로 확대하지 않고 실패합니다. 최대 12개월, 최대 150개 구·월·유형 조합입니다. 초기 전체 서울·20년을 한 번에 요청하지 마세요.

기준월은 서울 시간 현재 월까지입니다. from/to를 모두 비우면 전월~현재월입니다. 과거 해제·정정도 있으므로 최근월 수집만으로 과거까지 최신 상태가 되지는 않습니다.

로그는 범위·상태·건수·미매칭 건수·공개 여부·유지보수 상태를 기록합니다. 원본 XML·비밀키·거래 파일을 저장소/아티팩트에 올리지 않습니다. 일부 범위가 실패하면 workflow는 실패로 끝나지만 성공 범위는 유지됩니다. 같은 범위를 재실행할 수 있습니다.

확인할 항목:

- 저장 자료 다시 불러오기: 수집 구·월의 건수와 수집 시각
- 해당 단지 팝업: 계약일·면적·층·매매/전월세
- 매매 성공 / 전월세 미수집의 분리 표시
- 수집 완료 0건 / 미수집의 분리 표시
- 수집기를 멈춰도 공개 조회가 외부 API 호출이나 DB 쓰기를 유발하지 않는지

## 4. 자동 수집과 무료 한도

`MOLIT_SCHEDULE_ENABLED=true`와 명시적인 `MOLIT_DISTRICTS`가 있을 때만 매일 **한국시간 04:23** 실행 예정입니다. GitHub 스케줄은 지연/비활성화될 수 있어 실행 결과 확인이 필요합니다. 지정한 구의 전월·현재월 매매/전월세를 수집합니다.

**무료 운영을 보장하는 설정은 아닙니다.** D1 DB 크기·읽기·쓰기 한도가 있으며 인덱스 갱신과 삭제도 쓰기에 포함됩니다. 서울 전체 장기 내역은 단일 DB 용량 한도에 닿을 수 있습니다.

- 1개 구·1개월부터 건수, 실행 시간, D1 쓰기량/DB 크기를 측정합니다.
- 계정의 MOLIT 호출량·D1 한도·GitHub Actions 사용량을 함께 확인합니다.
- 대상 구와 주기를 예산 안에서 늘립니다. 검증 전에 스케줄을 켜지 않습니다.
- 한도 초과 시 무제한 재시도하지 않고 이전 완료 자료를 유지합니다.
- 과거 월은 별도로 나눠 재수집해야 취소·정정이 반영됩니다.
- 장기 차트를 위해 **활성 과거 월 스냅샷에는 TTL을 걸지 않습니다**.

공식 참고: [D1 한도](https://developers.cloudflare.com/d1/platform/limits/), [D1 쓰기 계산](https://developers.cloudflare.com/d1/platform/pricing/), [GitHub 예약 실행](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## 5. 안전장치와 정리

- 정수 만원 검증, 취소 매매 제외 후 건수를 expectedCount로 사용합니다. 비정상 유효 거래가 있으면 전체 범위를 보류합니다.
- 최대 200건/청크, 실제 본문 512 KiB. 작업 ID·순번·내용 해시로 재전송을 확인합니다.
- 완전한 건수일 때만 원자적으로 공개 버전을 교체합니다. 늦게 끝난 구버전이 최신 수집을 덮어쓰지 못합니다.
- 미매칭 원본 필드도 보관하고 단지 DB 적재 완료 여부에 의존하지 않습니다.
- 매칭 규칙 변경 시 `TRADE_MAPPING_VERSION`의 matcher suffix도 갱신하고 해당 범위를 재수집/재매칭해야 합니다. 저장된 complex_id는 자동 변경되지 않습니다.
- 공개 완료와 정리는 분리합니다. 1일 지난 비활성 작업을 최대 10회, 회당 원본 1,000행/가격 1,000행씩 정리합니다. 정리 실패는 수집 실패로 바꾸지 않습니다.
- `cleanupPending=true`이면 남은 정리/오류를 확인합니다. 로그의 최신 성공 id로 인증된 `/api/admin/trade-import`에 `{ "action": "cleanup", "id": "..." }`를 POST하고 remaining=false까지 한도를 보며 소량 반복합니다. 같은 구·월·유형만 정리하고 공개 head는 삭제하지 않습니다.
- 미완료 작업은 정리 전에 abandoned로 표시해 재개/공개를 차단합니다.

## 6. 실패와 롤백

- API 승인 전파 지연·잘못된 키·할당량·접속 오류: 기존 완료 자료 유지 후 해당 범위를 재실행합니다.
- 업로드 401: GitHub/Worker 토큰 일치 여부 확인.
- 503: DB 바인딩·마이그레이션·할당량·토큰 설정 확인. 비밀키 포함 URL을 로그에 출력하지 않습니다.
- 미수집은 완료 snapshot head가 없다는 뜻이며 거래 부재를 단정하지 않습니다.
- 필요 시 이전 Worker로 롤백하되 새 테이블은 삭제하지 않습니다. 이전 버전의 외부 API 직접 호출도 되돌아옵니다.
- 운영 복구 확인 전 기존 secret·데이터·이전 배포물을 지우지 마세요.
