# 내집어디 — 독립 서비스 전환 점검 (2026-09-07)

## 서비스 방향

- 대외 서비스명: **내집어디** (잠정 적용).
- 사용자: 서울에서 첫 집 또는 갈아탈 집의 후보를 좁히는 실수요자.
- 핵심 흐름: 예산·면적 → 지역·직장/지하철 조건 → 단지 비교 → 실거래·지도·학교 확인.
- 제이든 리서치는 하단 운영 주체로만 표기. 상세 패널과 검색·공유 제목에서 주 브랜드처럼 노출하지 않는다.
- 기존 매트릭스/결과 정렬/엑셀/상세 차트/지도 기능은 유지한다.
- 상표 등록 가능성, 같은 이름의 서비스, 도메인 등록 가능 여부는 별도 확인해야 한다.

GitHub 최신 main을 기준으로 정적 코드 점검과 자동 테스트를 수행한다. 수집 서버 응답 정상화, 실제 운영 DB 커버리지, 모바일 실기기·브라우저 화면 테스트를 확인했다고 간주하지 않는다.

기존 ChatGPT Sites가 active/owner 상태임을 확인했다. Sites도 Workers 기반 런타임이므로 단순 호스팅 복귀를 데이터 오류의 해결책으로 단정할 수 없다.

## 권장 운영 구조 — 아직 전체 구현 완료가 아님

공공데이터 → 제한된 별도 수집 작업 → 검증/중복·취소 반영 → DB → 공개 조회 API → 웹 화면

1. 단지 마스터를 먼저 전량 적재하고 현재 seed version의 exact/complete를 확인한다.
2. 실제 MOLIT 연결을 매매·전월세 각각 1개 구·1개월로 점검한다. 인증 성공, 응답 코드, 실제 계약 자료를 확인한다.
3. 수집기는 화면 요청과 분리한다. 처음에는 최근 3개월을 우선 수집하고 과거 자료를 작은 월/구 단위로 채운다. 공급자 승인 호출량을 지킨다.
4. 원본 거래와 수집 작업 상태를 영속 저장한다. district/month/type, fetchedAt, success/error, row count, 계약 취소/정정 내역을 관리한다.
5. 완전 수집한 월/유형만 교체한다. 일부 페이지 실패를 거래 0건으로 덮어쓰지 않는다.
6. 조회 화면은 DB를 읽는다. 수집 실패에도 마지막 성공 데이터를 보여 주되 실제 수집 시각과 계약일을 구분한다.
7. 전체 기간 차트는 월별 집계로 전송하고, 거래 목록은 페이지 단위로 가져온다.
8. 모든 공개 실거래/지도 조회에 호출 제한과 비용 상한을 설정한다. 관리자 수집 경로는 서버 비밀키로 보호한다.
9. 검색 최적화는 단지별 고정 주소·제목·대표 URL을 추가한 뒤 사이트맵으로 확장한다. 현재 팝업만으로 모든 단지가 개별 검색 노출되는 것은 아니다.

수집 위치(현 Workers / 기존 Sites / 별도 수집 실행 환경)는 동일한 조건의 연결 실측 후 결정한다. 별도 서버 구매·이전·유료 서비스 신청은 아직 실행하지 않는다.

## 이번 코드의 운영 설정

- PUBLIC_SITE_URL: 소유권과 연결을 확인한 대표 HTTPS 주소. 예: https://example.com
- DATA_REFRESH_TOKEN: 32자 이상 무작위 서버 비밀값. NEXT_PUBLIC_ 접두어, URL 쿼리, 브라우저 코드, 저장소에 넣지 않는다.
- 관리자 적재: POST /api/complexes?seedBatch=100 에 Authorization: Bearer <token> 헤더 사용. 응답 seedProgress.complete && exact를 확인하며 제한된 배치로 반복한다. 삭제나 재적재를 위한 기존 행 삭제는 하지 않는다.
- 기존 GET /api/complexes?seedOnly=1 는 이제 405를 반환한다. 운영 자동화가 이 URL을 사용 중이면 POST 방식으로 변경한 뒤 전환해야 한다.
- DATA_REFRESH_TOKEN을 설정하지 않으면 관리자 적재는 닫혀 있다. 일반 목록과 저장 가격 조회는 가능하다.
- 첫 방문은 국토부 실거래를 자동 수집하지 않는다. 저장 가격이 비어 있으면 가격 미확인으로 표시된다. 공공데이터 연결이 복구되었다는 뜻이 아니다.
- 네이버지도 Client ID는 공개 식별자지만 MOLIT/관리자 키는 비밀값이다. 기존 키를 변경하거나 읽어서 복사하지 않는다.

## 도메인 연결 방법

도메인은 사이트의 주소일 뿐 데이터 수집 오류를 해결하지 않는다. 도메인 구매·DNS 변경은 이번 작업에 포함하지 않는다.

### 현재 Cloudflare Worker를 유지할 경우

1. 이름 확정 후 등록 가능 여부와 갱신 비용을 확인하여 본인 계정으로 도메인을 구매한다. example.com은 설명용 예시다.
2. Cloudflare에 도메인을 추가한다. 기존 DNS(특히 이메일 MX/TXT)를 먼저 점검·보존하고, 등록기관에서 Cloudflare가 지정한 네임서버로 변경한다. 이미 설정된 DNSSEC가 있다면 공식 이전 절차를 따른다.
3. 도메인이 Active가 되면 Workers & Pages → seoul-apt-trade-dashboard → Settings → Domains & Routes → Add → Custom Domain으로 연결한다.
4. 해당 이름의 기존 CNAME 충돌 여부를 확인한다. 연결하면 Cloudflare가 DNS와 인증서를 구성한다. 기존 DNS를 무조건 삭제하지 않는다.
5. www 유무 중 대표 주소 하나를 선택하고 나머지는 리디렉션한다.
6. PUBLIC_SITE_URL을 대표 HTTPS origin으로 설정한 뒤 배포한다. 비밀키는 그대로 유지한다.
7. Naver Cloud → Application Services → Maps → Application의 Web 서비스 URL에 새 도메인을 해당 공식 가이드 규칙에 맞춰 등록한다.
8. HTTPS·단지 조회·매매·전월세·지도 동작을 확인한 후 네이버 서치어드바이저와 Google Search Console에 소유권을 등록한다. 검색 등록만으로 즉시 검색 노출이 보장되지는 않는다.

### 기존 Sites로 돌아갈 경우

기존 프로젝트를 유지하고 사용자 도메인을 Sites에 연결해 제공되는 소유권 확인/DNS 레코드를 적용하는 경로를 검토한다. 현재 Sites 소유권 확인은 되었지만 최신 코드 재배포·실거래 비교 검증은 완료하지 않았다. Cloudflare Workers의 Domains & Routes 설정을 Sites 주소에 그대로 적용하지 않는다.
