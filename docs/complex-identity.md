# 단지 식별자 정리 — 5단계 (2026-09-12)

## 이번 범위

이름 유사도를 이용해 전체 단지를 자동 병합하지 않습니다. 원본 필드의 근거를 검토한 **한 쌍**에만 대표 ID·이전 ID·별칭을 적용합니다. 다른 중복이 모두 해소되었다거나 서울 모든 아파트를 확보했다는 의미가 아닙니다.

근거는 저장소의 K-apt 원본 스냅샷인 [generated-complexes.json](../db/generated-complexes.json) (sourceUpdatedAt 2026-08-14)입니다. 지번 끝의 숫자 없는 하이픈은 별도 부번으로 보지 않습니다. 도로명주소와 검증된 좌표가 연결된 A13613001을 대표로 선택했습니다.

세대수·동수·주차대수를 합산하지 않습니다. 서로 다른 주차대수는 임의 보정하지 않고 대표 자료 151대를 유지하며 원본 156대도 그대로 남깁니다. 원천기관의 최신 확인에 따라 대표 선택은 재검토할 수 있습니다.

## 보존·조회 규칙

- 원본 K-apt/REB JSON 및 원본 메타데이터는 수정하지 않습니다.
- 원본 마스터 9,547행 → 표시용 대표 단지 9,546개. 검토된 별칭 ID 1개는 표시용 최신 membership에서만 제외합니다.
- 새 seed version으로 대표 membership을 적재합니다. 이전 D1 부모 행·membership·가격·거래를 삭제하거나 재배치하지 않습니다. 공개 GET은 읽기 전용입니다.
- 이전 ID로 팝업을 열거나 이전 이름으로 검색해도 대표 단지가 연결됩니다.
- 새 거래 매칭은 검토된 대표/별칭을 한 후보로 인덱싱합니다. 동일하게 정규화되는 여러 이름 때문에 같은 ID가 중복 후보로 들어가지 않습니다.
- 단지·면적별 저장 가격은 이전 ID와 대표 ID를 함께 읽어 동일 전용면적의 최신 계약일, 같은 날이면 높은 가격을 선택합니다. 단지별 기존 요약도 매매·전세·월세 각각 날짜와 가격을 같은 행에서 선택합니다. 기존 요약 건수는 중복 합산하지 않으며 정확한 거래 건수는 원본 저장 보고서를 사용합니다.
- 팝업 거래는 활성 스냅샷의 이전/대표 ID 행을 모두 읽습니다. 가격·날짜가 같은 별개 관측도 run ID+순번으로 보존하며 임의로 거래 건수를 줄이지 않습니다.
- 다른 지번의 강변그린(495-1/495-3), 보람(457-15/457-6), 홍익아파트(494-1/494-6)는 그대로 구분합니다.

## 좌표 수와 데이터 한계

좌표 원본은 추가하지 않았습니다. 기존 좌표 2,727개는 그대로이며 대표 단지 기준 미확인은 6,819개입니다. 원본 스냅샷의 기준은 여전히 9,547행 / 6,820개 미확인입니다. 차이 1개는 좌표를 새로 확보한 것이 아니라 좌표가 없던 중복 ID를 이미 좌표가 있는 대표에 연결한 결과입니다.

좌표 생성기는 원본 카탈로그 범위를 유지합니다. 화면의 TRANSIT_COVERAGE만 검토된 대표 ID 기준으로 계산하며 테스트가 원본·대표 범위의 정합성을 확인합니다.

## 운영 전환

1. PR 검토 및 배포 승인 후 새 코드를 배포합니다. 이 단계는 새 DB 스키마나 물리적 삭제를 요구하지 않습니다.
2. 기존 인증된 단지 적재 POST를 반복해 새 seed version membership을 완료합니다. 적재 중에는 검증된 내장 대표 마스터가 표시됩니다.
3. 구버전 매칭 결과가 미연결(NULL)이었던 거래는 읽는 동안 몰래 재분류하지 않습니다. 성북구의 필요한 월별 매매/전월세를 별도 수집기로 **완전 재수집**해야 새 기준이 적용됩니다. 새 작업 ID를 사용하세요.
4. 인증 status에서 expectedCount = storedCount = matchedCount + unmatchedCount, missingCount = 0을 확인합니다. 기존 NULL 원본은 보존되며 미연결 건수로 구분됩니다.
5. 새 스냅샷이 완전히 저장된 뒤에만 활성 자료가 교체됩니다. 부분 수집으로 기존 공개 자료를 덮어쓰지 않습니다.

이미 요약 저장 단계에서 누락된 거래는 이 코드만으로 복원되지 않습니다. 실제 운영 D1/MOLIT 백필이나 공개 배포는 이번 PR 작업에서 실행하지 않았습니다.

## 후속 검토·회귀 검증

새 병합은 lib/complex-identity.mjs에 근거를 기록하고 버전을 올린 뒤 검토합니다. 원본 업데이트로 ID·구·동·지번·승인일·년도·세대·동수·이름 근거가 바뀌면 빌드 시 검증이 실패하므로 자동으로 잘못 병합하지 않습니다. 지번뿐 아니라 동별 분리/임대·분양/단계별 단지 여부를 확인해야 합니다.

검증 항목: 실제 원본 한 쌍 및 다른 지번 3쌍, 구버전 ID/별칭 검색, 지번/이름 매칭, 미연결 보존, 동일 내용의 별개 거래, 실제 SQLite의 기존 membership/부모/가격/면적 보존, 전용면적별 최신 가격, 매매·전세·월세 상세, 공개 API 읽기 전용, 구버전 NULL의 완전 재수집 후 연결.
